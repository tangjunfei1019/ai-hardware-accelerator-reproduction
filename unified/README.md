# Unified runnable evaluation path — SCALE-Sim (v3)

One framework, same workload, comparable numbers — instead of one original
Python skeleton per paper.

## Framework

- **Framework:** SCALE-Sim, scalesim-project/SCALE-Sim (systolic-array simulator)
- **Upstream clone:** `~/workspace/scalesim-upstream/`, HEAD `9f98c4371055a54c75209c2e02b640b897550532`
  (cloned 2026-11-02; separate folder, not inside the repo; nothing pushed)
- **Run environment:** CPU-only, 4 vCPUs, 7.7 GB RAM, no GPU, no Docker.
- **Dependencies actually needed:** system Python 3.12.3 with numpy 1.26.4,
  pandas 2.1.4, matplotlib 3.6.3, plus `tqdm` 4.70.1 (installed with
  `pip3 install --break-system-packages --user tqdm`).
  The upstream `requirements.txt` also lists numba/absl-py/cython, but no
  file under `scalesim/` imports them, so they were not installed and the
  runs below did not need them.
- **Run from source (no pip install of SCALE-Sim itself):**
  `PYTHONPATH=<scalesim-upstream> python3 scalesim/scale.py -c <config> -t <topology> -p <output>`

## Workloads and configs (exact commands)

All three runs below were executed 2026-11-02 from
`~/workspace/scalesim-upstream/` with `PYTHONPATH=$PWD`.

### Run A — TPU-like array (maps to paper 06, TPU)

```bash
PYTHONPATH=$PWD python3 scalesim/scale.py \
  -c configs/google.cfg \
  -t topologies/conv_nets/test.csv \
  -p <unified>/logs/google_test
```

Config `google.cfg`: 256×256 array, output-stationary dataflow,
IFMAP/Filter SRAM 6144 kB each, OFMAP SRAM 2048 kB, USER bandwidth 10.
Workload `test.csv`: one conv layer, IFMAP 7×7, filter 3×3, 192 channels,
384 filters, stride 1.

### Run B — Eyeriss-like array (maps to paper 05, Eyeriss)

```bash
PYTHONPATH=$PWD python3 scalesim/scale.py \
  -c <unified>/eyeriss_v3.cfg \
  -t topologies/conv_nets/test.csv \
  -p <unified>/logs/eyeriss_test
```

Config: upstream `configs/eyeriss.cfg` (12×14 array, weight-stationary,
36 kB SRAM each) **plus one locally added `[layout]` section**
(see `eyeriss_v3.cfg` in this folder). The upstream file has no `[layout]`
section and fails under SCALE-Sim v3 with
`configparser.NoSectionError: No section: 'layout'` — that is an upstream
config-format gap, not an architecture change; array, dataflow and SRAM
sizes are unchanged from upstream.
Same workload as Run A, so A and B are directly comparable.

### Run C — sparsity (maps to paper 10, SCNN, only in the sparsity sense)

```bash
PYTHONPATH=$PWD python3 scalesim/scale.py \
  -c configs/sparsity.cfg \
  -t topologies/sparsity/conv.csv \
  -p <unified>/logs/sparsity_test
```

Config `sparsity.cfg`: 128×128 array, weight-stationary, sparsity on
(ellpack_block, 2:4-style, block 8). Workload `conv.csv`: one tiny conv
layer, IFMAP 5×5, filter 3×3, 2 channels, 6 filters, stride 1,
sparsity 2:4. **Note:** this is a different, much smaller workload than
Runs A/B, so its cycle count is NOT comparable to A/B — it only proves
the sparsity path runs here.

## Results (from the COMPUTE_REPORT.csv files in `logs/`)

| Run | Array / dataflow | Total cycles (incl. prefetch) | Compute cycles | Stall cycles | Overall utilisation | Mapping efficiency |
|---|---|---|---|---|---|---|
| A — TPU-like (`google.cfg`) | 256×256, output-stationary | 93,908 | 4,475 | 0 | 5.66% | 7.32% |
| B — Eyeriss-like (`eyeriss_v3.cfg`) | 12×14, weight-stationary | 249,102 | 245,951 | 0 | 40.15% | 97.96% |
| C — sparsity (`sparsity.cfg`) | 128×128, weight-stationary, 2:4 sparsity | 432 | 390 | 0 | 0.02% | 0.24% |

Bandwidth (SRAM, words/cycle, from stdout):

- A: IFMAP 19.307, Filter 148.280, OFMAP 2.374; DRAM 10.000 each.
- B: IFMAP 4.918, Filter 2.698, OFMAP 5.621; DRAM IFMAP 9.831, Filter 2.689, OFMAP 5.665.
- C: IFMAP SRAM 357.087, Filter SRAM 0.246, OFMAP SRAM 0.138; DRAM 50 / 50 / 27.

Runtime: Run A finished in seconds; Run B in ~20 s (including trace
writing); Run C in under a second. Full per-layer reports are in
`logs/<run>/…/COMPUTE_REPORT.csv`, `BANDWIDTH_REPORT.csv`,
`DETAILED_ACCESS_REPORT.csv` and `TIME_REPORT.csv` (plus
`SPARSE_REPORT.csv` for Run C). The large cycle-accurate `*_TRACE.csv`
files (105 MB total) were deleted from this evidence folder to keep it
small; they can be regenerated by re-running the commands above.

## What this proves

- SCALE-Sim v3 **does run on this VM** (CPU-only, no Docker, no C++
  build, no GPU) for small workloads, and the same workload can be run
  through two different array/dataflow configs to give comparable
  cycle/utilisation numbers. That is the unified path the repo was
  missing: papers 05 and 06 can now be compared on one framework's
  axes instead of only in prose.
- The A-vs-B contrast is real and instructive: on this tiny 7×7 layer
  the 256×256 TPU-like array is only 5.66% utilised (the layer is far
  too small for it), while the 12×14 Eyeriss-like array reaches 40.15%
  utilisation and 97.96% mapping efficiency. Array size must match the
  workload — a point worth stating in the comparison matrix.

## What this does NOT prove (read before quoting any number)

- **These are SCALE-Sim framework estimates, not paper results and not
  silicon measurements.** They do not reproduce any TPU, Eyeriss or
  SCNN paper accuracy, throughput or energy figure, and must never be
  quoted as such.
- **A and B are not perfectly apples-to-apples:** upstream `google.cfg`
  runs in USER bandwidth mode (bandwidth 10), while `eyeriss.cfg`
  runs in CALC (estimate-bandwidth) mode. The utilisation contrast is
  still meaningful, but a stricter comparison should force the same
  bandwidth mode in both configs.
- **Run C is not comparable to A/B** (different workload, different
  array) and its 0.02% utilisation only reflects how tiny its workload
  is on a 128×128 array. It does not validate SCNN's sparsity gains.
- **No energy numbers:** Accelergy integration was not run (it needs
  extra setup); the reports here are cycles/utilisation/bandwidth only.
- **A larger workload was tried and abandoned:** the YOLO-tiny first
  layer (416×416, `yolo_tiny_layer1.csv`) under `google.cfg` was
  progressing at ~359,790 trace steps and was killed after reaching
  ~39% — it would have taken far longer than a demo run. Keep unified
  workloads small on this VM, or run larger ones on a bigger machine.
- **Timeloop was not attempted:** SCALE-Sim was tried first and succeeded,
  so the multi-hour C++ Timeloop build was not started. Timeloop/Accelergy
  remains the heavier alternative if energy/area estimates are wanted later.
- **In the repository:** this folder is committed in the repo and linked from papers 05, 06 and 10 (`code/CODE.md`).
